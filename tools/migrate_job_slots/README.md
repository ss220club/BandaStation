# Offline-конверсия назначений профилей

Этот отдельный Python 3.11+ инструмент не подключается к DME и не запускается при входе игрока. Он позволяет заранее проверить и массово конвертировать сохранения с резервной копией при остановленном сервере. Runtime также читает корректный старый формат и объединяет его с `pref_job_slots` до первого вложенного native save, поэтому внешняя конверсия не является условием сохранности корректных назначений. Агент не запускает инструмент против production без отдельного разрешения.

При повреждённой карте runtime сохраняет оба исходных entries и их наличие, отклоняя set/reset назначений до исправления данных; остальные настройки можно сохранять. Offline-инструмент строже проверяет JSON и структуру всего сохранения. В частности, он различает boolean и число, которые после DM `json_decode` уже неразличимы. Его отказ нельзя считать успешной runtime-конверсией.

Формат подтверждён по `code/modules/client/preferences_savefile.dm::load_path/load_preferences/save_preferences` и `code/datums/json_savefile.dm`: `data/player_saves/<первая буква ckey>/<ckey>/preferences.json` содержит корневые настройки игрока (`version`, `default_slot`), корневые карты назначений и отдельные вложенные `characterN`. Конверсия обрабатывает только `*/*/preferences.json` внутри явно выбранного корня, проверяет путь и корневую структуру. Поддерживаемые версии сохранения: 32–53, как в этой ревизии игры. Версия 53 меняет key bindings в штатном runtime; offline-инструмент сохраняет их без изменений. Более новые/устаревшие версии, обёртки, повреждённые character-секции, повторные JSON-ключи и неправильные карты отвергаются.

Положительные `job_assigned_profiles` переносятся в `pref_job_slots`. Любое явное новое значение, включая `0` и `-1`, побеждает старое. Затем старый корневой ключ удаляется. `[]` и `null` означают пустую DM-карту. Верхняя граница слота здесь не ограничивается: потеря доступа к сохранённому слоту не должна уничтожать назначение. Остальные поля и содержимое character-секций сохраняются; преобразование идемпотентно.

1. Остановите сервер и другие процессы записи сохранений. Сохраните полную независимую резервную копию `player_saves`.
2. Запустите просмотр изменений (это режим по умолчанию; файлы, backup и временные файлы не создаются):

   ```powershell
   py -3 -B tools/migrate_job_slots/migrate.py D:\Server\data\player_saves
   ```

3. Разберите все `ERROR`. Файл с неожиданной структурой или повреждёнными значениями остаётся нетронутым, без reset. Отчёт показывает относительные пути и причины, без значений настроек. Не развёртывайте новую runtime-версию, пока не обработаны все отказавшие файлы.
4. Укажите новый каталог backup вне `player_saves` и подтвердите остановку всех писателей:

   ```powershell
   py -3 -B tools/migrate_job_slots/migrate.py D:\Server\data\player_saves --apply --server-stopped --backup-dir D:\Backups\job-slots-before-deploy
   ```

Для каждого изменяемого файла сначала создаётся точная копия исходных байтов по тому же относительному пути в backup. Существующий backup не перезаписывается. Затем данные записываются во временный файл рядом с исходным и заменяются атомарным `os.replace`; перед заменой проверяется, что исходные байты не изменились. Ошибка записи оставляет исходный файл и backup для восстановления; временный файл удаляется. Флаг остановки — подтверждение оператора, он не завершает процессы сам. Не изменяйте сохранения параллельно конверсии.

Инструмент продолжает отчёт по остальным файлам при ошибке. Код выхода `0` означает успешную проверку/конверсию всех найденных файлов; `1` — как минимум один отказ; `2` — ошибка запуска или пустой/неправильный корень. При повторном apply уже конвертированные файлы и backups остаются нетронутыми. Для повторного восстановления из частичного сбоя используйте отдельный новый backup-каталог после проверки причин.

Регрессионные проверки конвертера вынесены во внешний набор вместе с тестами расширений. Они запускают этот инструмент на синтетических TEMP-сохранениях; реальные сохранения не используются. Тестовые файлы не входят в игровой репозиторий.

После конверсии повторный dry-run должен показать `changed=0 errors=0`. Храните backup отдельно от игрового кода; возврат данных выполняйте при остановленном сервере из полной резервной копии, если понадобится откат развёртывания.

## Проверка готовности для предварительной конверсии

`py -3 -B tools/migrate_job_slots/migrate.py <player_saves> --check-ready` ничего не записывает. Код 0 означает, что все найденные файлы прошли проверку и не требуют конверсии; 1 — ошибка или оставшаяся конверсия; 2 — неправильный запуск/путь или отсутствие файлов. Обычный dry-run сохраняет прежнюю семантику и сам по себе не блокирует запуск при `changed > 0`.

На Windows используйте `start_checked.ps1 -PlayerSaves <player_saves> -ServerCommand <команда-запуска> -ServerArguments <аргументы>` из рабочего каталога сервера. Эта обёртка запускает команду только после успешного `--check-ready`; она не конвертирует сохранения и не останавливает процессы. Для службы/контейнера поставьте ту же read-only проверку перед штатным запуском и прерывайте запуск при любом ненулевом коде. Проверяемый каталог должен быть тем же каталогом, который использует запускаемый сервер.

Пустой каталог намеренно не считается доказательством конверсии: для действительно нового развёртывания без сохранений требуется отдельное подтверждение оператора. Проверка должна выполняться после остановки прежнего экземпляра и перед запуском нового, без параллельных писателей. Она проверяет формат назначений, а не полную игровую совместимость персонажей.

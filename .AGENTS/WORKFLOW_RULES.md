# Модуляризация и проверка результата

## Сначала установи рабочий путь

Прочитай точный запрос, текущую реализацию, includes, overrides/signals, callsites и потребителя результата. Установи владельца состояния, возможные ожидания и побочные эффекты. Для существенной задачи запиши цель, узкие пути, MUST/KEEP/REJECT/CHECK и проверяемые допущения в [task state](TASK_STATE.md).

Сохраняй чужие dirty-изменения. Не переименовывай переменные, не форматируй и не рефактори соседние алгоритмы ради удобства нового модуля. Перед генератором установи все входы и перезаписываемые выходы.

## Как расширять upstream

Новая логика, состояние и файлы BandaStation живут в `modular_bandastation/`. Выбирай простейший подход, сохраняющий штатный контракт:

| Потребность | Подход |
| --- | --- |
| Достаточно настроить объект | Поля subtype либо изменение собственного состояния после инициализации |
| Есть сигнал или hook | Используй его, проверь момент вызова и контракт обработчика |
| Условие до штатного действия | Проверка в модульном override, затем вызов родителя |
| Дополнительные возвращаемые данные | `. = ..()`, затем изменение результата |
| Нужна точка внутри процедуры | Минимальная локальная инъекция; реализация и состояние — в модуле |

Реальный пример include/lifecycle: [example/_example.dme](../modular_bandastation/example/_example.dme) и [example/_example.dm](../modular_bandastation/example/_example.dm). Там модпак сохраняет родительские фазы через `. = ..()`. Новый файл должен входить в действующий include graph.

### `..()` и `.`

`..()` вызывает родительскую реализацию, `.` — возвращаемое значение текущей процедуры. `. = ..()` сохраняет результат родителя и позволяет дополнить его. `return ..()` завершает текущую процедуру с результатом родителя; после него дополнение не выполнится.

Следующие примеры — учебные схемы, а не существующие API. Подставляй реальные сигнатуры, аргументы и коды результата из исходников.

Проверка до побочных эффектов:

```dm
/datum/example/perform(mob/user)
	if(!module_allows(user))
		return FALSE
	return ..()
```

Дополнение возвращаемых данных:

```dm
/datum/example/get_data()
	. = ..()
	// Здесь контракт родителя гарантирует list; Copy сохраняет его общий объект.
	var/list/native_data = .
	. = native_data.Copy()
	.["module_value"] = module_value
```

Проверь тип и смысл результата: например, `JOB_AVAILABLE` равен `0`; `if(!.)` не означает ошибку допуска. Не добавляй фиктивный вызов родителя ради формальной отметки. Один вызов `..()` может уже создать тело, выдать вещи или сохранить данные — изменение `.` не отменит эти действия. Проверку, запрещающую действие, ставь до него; rollback выполняй до удаления необходимых объектов.

Списки могут быть общими: перед изменением создай собственную копию, если этого требует контракт; `Copy()` не делает глубокую копию вложенных списков. Не подменяй глобальные job datums или активные preferences на время вызова, который может ожидать. После диалога/ожидания повторно проверь клиента, владельца и относящееся к запросу состояние.

### Узкая внутренняя инъекция

Если override не получает нужных локальных данных или вызывается слишком рано/поздно, допустима узкая точка подключения. Пример схемы внутри существующей процедуры:

```dm
	native_validate()
	// BANDASTATION EDIT START - Feature admission
	if(!module_can_continue())
		return FALSE
	// BANDASTATION EDIT END - Feature admission
	native_commit()
```

`module_can_continue()` определяется в модуле. Выбор точки обязан учитывать побочные эффекты предыдущих фаз и завершение отказа. Штатная последовательность остаётся рабочей; не переносится в копию в модуле. Для каждого core-hunk запиши назначение, модуль-владелец и причину, по которой существующего override/сигнала недостаточно.

Одну добавленную строку отмечай `// BANDASTATION EDIT - <причина>`. Несколько строк заключай в `// BANDASTATION EDIT START - <причина>` и `// BANDASTATION EDIT END - <причина>`. Не повторяй inline EDIT внутри блока. Собственные модульные файлы такими метками не обрамляй.

Не допускаются:

- Полная копия штатного алгоритма в модуле вместо расширения.
- Сохранённый оригинал за безусловным ранним `return alternative()` или фиктивным predicate, выключающим native-ветку.
- Обход необходимого родителя вызовом конкретного далёкого предка.
- Перестройка upstream ради уменьшения числа модульных hooks или косметического diff.

Если без удаления/замены upstream не сохраняется корректность, а запрос этого не разрешает, предъяви конкретный конфликт и узкий diff исключения. Не расширяй разрешённую область самостоятельно. Явный запрос пользователя определяет scope; обычные решения внутри него не требуют отдельного согласования. Разрешённую замену старого пути не подменяй сохранением fallback.

## Где брать код-стайл

Источники: [STYLE](../.github/guides/STYLE.md), [STANDARDS](../.github/guides/STANDARDS.md), [AUTODOC](../.github/guides/AUTODOC.md), [CONTRIBUTING](../.github/CONTRIBUTING.md), [TGUI README](../tgui/README.md). Проверяй актуальные конфиги линтеров и стиль соседнего кода; старые нарушения не оправдывают новые.

Для DM: табы, полные typepaths, статические типы вместо доступа через `:`, понятные имена и константы. Учитывай контракт сигналов, `SIGNAL_HANDLER` и запрет ожидания в синхронном обработчике. Не дублируй алгоритмы. У цикла должен быть прогресс; отдельно проверь nested/associative list-семантику.

Для TGUI сначала проверь DM `ui_data/ui_act`, реальный компонент и существующие точки композиции. Добавляй модульный компонент через узкое подключение, используй штатные компоненты и стили. Не заменяй весь интерфейс, dispatcher или render ради одного дополнения.

## Как принять результат

| Изменение | Проверка |
| --- | --- |
| DM | Includes/callsites, штатная сборка, относящийся unit/runtime сценарий |
| TGUI | DM-контракт, lint/types/tests по области, реальная страница и кадр |
| Карты/ресурсы | Include/binding, maplint или DMI-проверка; runtime/кадр для поведения и внешнего вида |
| Переводы | Исходные TOML fragments, merge/schema и потребитель; generated файл вручную не править |
| Агентский набор | `tools/agents/check.ps1`, Git-границы, целевые сценарии |
| MCP/установщик | Чистая установка/повтор, initialize → tools/list → tools/call → shutdown |

Build targets сверяй с `tools/build/build.ts` и [build README](../tools/build/README.md). DreamMaker-only не проверяет весь pipeline. Браузерный MCP проверяет веб-страницу, а не полноценный BYOND runtime.

Смотри весь diff к базе задачи, а не только последний коммит: штатные алгоритмы действительно вызываются, нет копий, неисполняемых хвостов и лишних обёрток. Compile PASS этого не доказывает. Выполни `git diff --check`, обнови TODO/evidence и укажи ограничения. Не повторяй успешные проверки без нового изменения или неопределённости.
